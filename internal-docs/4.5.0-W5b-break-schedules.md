# 4.5.0 W5b: break schedules, lateness text and flicker

Status: **MANUALLY_VERIFIED** 2026-11-06 (owner live test passed; GitHub emulator 206/206 on the strict rules). Not PRODUCTION_APPROVED.
W5a (floating clock) was MANUALLY_VERIFIED by the owner on 2026-11-06.

## What it does
- New card **WorkTrack > Break schedules**: allowed minutes for First break, Lunch and Last break, for a **Default** and for each **active Client ID**. `0 = no limit, never late`. Search box and "Show more" (50 at a time, always "Showing X of N"); no silent cap.
- Which schedule is used: the first client added to the session (earliest `addedAt`, ties: alphabetical Client ID); if that client has none, the **Default** (never the second client); if there is no Default, the built-in **15 / 60 / 15**.
- While a break is open the WorkTrack page and the floating clock show "Lunch: 42:10 left" or "Lunch: late by 03:12" and which schedule is in force. "Near" (5 minutes, or half the limit if shorter) turns the text amber.
- When late, the matching "in" button gets a class that pulses once every 1.2 s (page and clock). Switch it off per device with "Flicker the button when a break is late". With reduced motion the pulse is replaced by a steady thick outline. Late is always also written as text, and announced once to screen readers.
- Deadline = the **database time of the break-out punch** + allowed minutes. Late only when strictly past the deadline.

## Revision 2 (QA review) items built here
- **R2**: an edit applies from the **next** break. Each schedule stores the previous minutes (`pfb`, `plu`, `plb`) and the time of its last edit; a break whose break-out punch is older than the last edit keeps the previous limit. The rules force the stored previous values to equal the values being replaced, so they cannot be forged.
- **R3**: schedules are re-read at every full load (sign-in, page open, own punch, a changed revision found by the 60-second focus check): the schedule client's document and `default`, two reads at most.
- **R4**: a schedule document ID must be `default` or a Client ID that exists in the registry (checked in the rules and in the screen, which lists active clients only).
- **R5** search and "show more". **R6** "0 = no limit, never late" next to every field.

## Data and rules
`workSchedules/{default | ClientID}`: `{ fb, lu, lb, pfb, plu, plb, rev, updatedAt }`, whole numbers 0 to 240, `rev` 1 on create then +1, `updatedAt` = database time. Owner only (read, list, create, update, delete); public, Google strangers and visitor tokens get nothing. Added at the **end** of both `firestore.rules` and `firestore.rules.strict`. **Republish `firestore.rules.strict`.** No punch, state-machine, session, assignment or log rule changed.

## What it does NOT do
Lateness is **display only**: it is not stored on a punch, in a report or in the sealed log (that would be a later phase). Deleting a schedule while a break is running makes that break use the Default or built-in values. Editing a schedule twice during one single break uses the middle values for that break (rare: you are the only worker).

## Database cost (free plan)
- Each full load with an open session: +1 to 2 reads (schedule client document and Default). No session open: 0.
- Opening WorkTrack: one read of the schedules collection (as many reads as schedules saved, at most one per client plus Default).
- Saving: 1 transaction (1 read + 1 write). Nothing polls.

## Honest limits
- Real database, Safari, real touch and screen reader not tested. The clock estimate can be about 1 second off; the deadline itself uses the database punch time.
- A second device sees a schedule edit at its next full load (own punch, sign-in or a changed revision), not instantly. A break already running is never changed by an edit, so a stale view cannot make it late wrongly.
