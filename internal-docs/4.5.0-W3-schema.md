# 4.5.0 W3 - corrections, sealed log, settings (internal)

This repository is public. Nothing secret belongs in this file.

## Collections (owner only)
| Path | Fields | Notes |
|---|---|---|
| `workCorrections/{id}` | sid, kind (TIME/ADD/CLIENT_ADD/CLIENT_REMOVE), n, type, clientId, at, at2, reason, closeEid, closeN, by, createdAt | Create-only. | `workSeals/{hash}` | n, prev, hash, kind (genesis/records), ids, upto, legacyN, at, by | Create-only; ID = hash. genesis: n=1, prev=zeros, covers every record with time <= upto (legacyN of them). records: n>=2, ids = paths of covered records (1..30). |
| `workChain/main` | cn, head, updatedAt | Created with the genesis seal; each update is paired with the new seal: cn+1, head = new seal hash, seal.prev = old head. |
| `workSettings/main` | tz, weekStart, prevTz, prevWeekStart, rev, updatedAt | tz applies to NEW sessions only. Update keeps the replaced values. |

## Seal fingerprint
`SHA-256("CFW3|" + n + "|" + prev + "|" + kind + "|" + records.join(";"))`, each record `path=` + key-sorted JSON with times as milliseconds. Covered collections: workEvents (at), workSessions (startedAt), workAssignAudit (createdAt), workCorrections (createdAt). Records are read back after writing so the server times are inside the fingerprint. Verify recomputes everything, checks numbering, links, the chain head and records that no seal covers.

## Why seals are a second write
Server times are unknown before the commit, so the records are written exactly as in W1/W2 (rules unchanged) and sealed right after. A failed seal leaves records "waiting"; Verify lists them and one button seals them. Older unsealed records are a reported problem.

## Honest limits
Rules cannot compute SHA-256. Detection, not prevention. The newest seal needs the witness copy. Day-order validity of a correction is checked by the page.
