# 4.5.0 F5 - Form verification: Worker, rules, switch (setup and runbook)

This repository is public, so nothing secret belongs in this file. Keys, secrets and the signing account are created by the owner in the Google and Cloudflare dashboards.

## What it is
A visitor who wants to send the Meeting Request form first asks the **portfolio-forms** Worker for a small challenge (a six-digit code the page shows and the visitor types). If the code is right, the Worker signs a **Firebase custom token** that is valid for 10 minutes and carries the claim `form = meeting` and a random user ID `m_` + 16 characters. The page signs in with that token and writes the request straight to Firestore. The Firestore rules accept the write only if:
1. the sign-in is a custom-token sign-in with `form = meeting` and an `m_...` user ID;
2. the request's document ID equals that user ID (one request per token, single use);
3. the request's `day` field is today (UTC, from the server clock) and the **daily counter** `reqCounters/{YYYYMMDD}` was bumped by exactly +1 by the same token in the same batch (the "stamp");
4. the counter is still under the daily cap (`content/guard.cap`, default 30);
5. every existing check still passes (pause, capacity, busy slot, field sizes, e-mail shape, server time).

## The switch (`content/guard.tokenRequired`)
| Value | Old direct form (today's page) | Token path |
|---|---|---|
| field absent or `false` (default) | **works, unchanged** | works |
| `true` | refused | works |

F5 publishes the rules with the switch **off**, so the live form behaves exactly as before. F7 flips it. Setting it back to `false` is the instant rollback (no republish needed). The field must be the boolean `true`; the text "true" or the number 1 does not count.

## Honest limits
- The code is sent to the page, so a script can read it. It is a speed bump, not a CAPTCHA.
- Real limits: per-visitor throttles in the Worker (per Worker instance, approximate: 8 challenges, 3 tokens, 12 wrong codes per address per 10 minutes; 3 wrong tries per challenge), single-use tokens, and the **exact** daily cap in the rules.
- An attacker can still fill the daily cap (lock-out). Mitigations: the mailto fallback in F6, the owner can raise the cap or pause, and the cap is only 30 spam entries, not unlimited writes.
- Every token creates one Firebase Authentication user. They pile up (about one per submission attempt that gets a token). Clean up once a month: Firebase Console > Authentication > Users > delete users whose ID starts with `m_`. Counters are one small document per day and need no cleanup (the rules do not allow deleting them; the owner can delete from the console).
- The Worker reads `content/guard` (public read) to learn about a pause; if that read fails it stays open and the rules still enforce the pause.
- Free-plan Worker limits: 100,000 requests/day, 10 ms CPU. Signing measured 2 to 3 ms (cold 2 ms) in the F3 spike.

## Owner setup (once)
1. **Service account (blocking check).** Google Cloud Console, project `my-online-portfolio-db2a5` (pick it in the top bar) > IAM & Admin > Service accounts > Create service account. Name `portfolio-form-signer`. **Do not give it any role.** Open it > Keys > Add key > Create new key > JSON. The file downloads once. If the console says key creation is blocked by an organisation policy, stop and tell Claude.
2. **Worker.** Cloudflare dashboard > Workers & Pages > Create > Hello World > name `portfolio-forms` > Deploy > Edit code > replace everything with `server/portfolio-forms-worker.js` > Deploy.
3. **Secrets** (Worker > Settings > Variables and Secrets):
   - `SA_JSON` (Secret): paste the **whole content** of the JSON key file.
   - `CH_SECRET` (Secret): 40 or more random characters.
   - `ALLOWED_ORIGINS` (Text): `https://fredespinosa86app-jpg.github.io` (add your own domain later, comma separated, no path).
   Deploy again after adding them.
4. **Check.** Open `https://portfolio-forms.<your-subdomain>.workers.dev/v1/status` in a browser. A browser address bar sends no Origin header, so the answer **`{"error":"origin"}` (403) is the correct, healthy result**. The real check is made by the page in F6/F7.
5. **Delete the key file** from your computer after step 3 (the Worker holds the only copy you need; you can create another any time).
6. **Rules.** Run the GitHub workflow "Firestore rules (emulator)" (Actions tab > Run workflow). When it passes, publish `firestore.rules.strict` in Firebase Console > Firestore Database > Rules. The switch is off, so nothing visible changes.

## Rollback
- Switch: set `tokenRequired` to `false` (Security page toggle comes in F6; until then the Firebase console, document `content/guard`).
- Rules: publish the previous `firestore.rules.strict` (in the rollback ZIP). The old form keeps working with either file.
- Worker: delete or disable it; nothing else depends on it until F6.
