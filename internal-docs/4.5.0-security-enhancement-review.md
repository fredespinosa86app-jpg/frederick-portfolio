# Security enhancement review list (status: DESIGNED, nothing built)

Source: the owner's request after the 2026-11-06 rating (overall about 85% for this kind of site, up from about 70%). These five items are what keeps the rating from 90% or more. Each needs the owner's approval before a build (layout first, then build, tests, ZIP + rollback ZIP, checklist, commit text, live test).
Related items already on the list and not repeated here: retention of other data, streamed size limit in the chat Worker (chat is scripted only), keep backup exports, Training icon buttons on the other dashboard pages.

## Recommended order
E3 (SDK pinning) -> E1 (App Check) -> E5 (review preparation) -> E4 (navigation and calendar frames) -> E2 (headers via Cloudflare, only if the owner moves the domain).
Reason: E3 is small and removes a supply-chain risk with no owner setup; E1 has the largest effect on abuse but needs console steps and has failed once; E5 can run in parallel; E4 depends on which calendar provider the owner really keeps; E2 is the biggest change and optional.

## E1. App Check is not enforced (bots, free-quota exhaustion)
- **Today:** the code supports App Check (`owner-panel.js`, `form-guard.js`; `settings.js` `appCheckSiteKey` is empty). An earlier attempt with reCAPTCHA Enterprise got HTTP 400 from Google. Form verification (the Worker, rate limit, daily cap) limits abuse but does not stop a bot that follows the flow.
- **Risk:** medium for the form and the free quota. Quota exhaustion cannot be proved or disproved from here.
- **Options:** (a) reCAPTCHA v3 provider (`appCheckProvider: "v3"`, marked deprecated in the code comment), (b) retry Enterprise with the current Google console steps, (c) leave in monitoring-only mode and watch the metrics first (no enforcement).
- **Plan:** 1) owner registers the site in Firebase > App Check and sends the site key (a public key, not a secret); 2) set `appCheckSiteKey` and provider; 3) add the three Google hosts to `connect-src` (`www.google.com`, `recaptchaenterprise.googleapis.com` or the v3 hosts, `content-firebaseappcheck.googleapis.com`); the guard test already fails until they are there; 4) run in MONITOR mode for 7 days and read the verified/unverified ratio; 5) only then enforce for Firestore; 6) rollback: switch enforcement off in the console (no deploy needed).
- **Tests:** guard test (hosts), browser test for the token request path with the stub, live checklist (form still works, ratio visible).
- **Needs from owner:** Firebase console steps, the site key, a decision on the provider, and a 7-day monitoring window. **Risk of the change itself:** enforcing too early blocks real visitors, so enforcement is a separate, later step.

## E2. No real security headers (GitHub Pages cannot send them)
- **Today:** the CSP is a meta tag; there is no `frame-ancestors`, `X-Content-Type-Options`, `Referrer-Policy` or `Permissions-Policy` header. A frame-guard script covers clickjacking partly.
- **Risk:** low to medium (clickjacking, MIME sniffing); meta-tag CSP also cannot report-only.
- **Options:** (a) do nothing (documented limit), (b) move the domain `frederickespinosa.com` (currently at Hostinger and not serving the portfolio, no email on it) to Cloudflare DNS, point it at GitHub Pages, and add response-header rules in Cloudflare (to be confirmed against Cloudflare's current documentation at build time), (c) host on Cloudflare Pages, which supports a `_headers` file.
- **Plan if approved:** 1) owner decides about the domain move (changes DNS and the site address, `canonical`, `sitemap`, `robots`, `security.txt` and the Google sign-in authorized domains must all be updated); 2) add header rules and a report-only CSP first; 3) then move the CSP from meta to header, keep the meta as a fallback; 4) update `S2` checklists; 5) rollback: DNS back to Hostinger or remove the rules.
- **Needs from owner:** a clear yes to the domain move and its consequences. This is the largest and most disruptive item; do it last or not at all.

## E3. Firebase SDK is loaded from Google's servers with no pinned integrity (supply chain)
- **Today:** `form-guard.js` and `owner-panel.js` import `https://www.gstatic.com/firebasejs/10.12.2/*.js`. The version is pinned in the URL, but the files themselves are not checked, and `script-src` trusts `www.gstatic.com`, `apis.google.com`, `accounts.google.com` and `www.google.com/recaptcha/`.
- **Risk:** low probability, high impact (a changed file would run with full page powers).
- **Options:** (a) self-host (vendor) the exact SDK files under `assets/vendor/firebase/10.12.2/` and import them from the same site, then remove `www.gstatic.com` from `script-src`; (b) integrity attributes through an import map (browser support for module integrity should be verified before relying on it); (c) leave as is.
- **Recommendation:** (a). The download must come from the owner's machine or a network that can reach gstatic (this workspace may not). Updates become manual, so add a quarterly note to check Firebase release notes for security fixes.
- **Plan:** 1) owner or I fetch the files for the exact version and record their SHA-256 in a manifest; 2) a test fails if a vendored file's hash changes or if any `gstatic.com` URL appears in the code; 3) switch the two import bases; 4) tighten `script-src`; 5) full regression and a live test of sign-in, form verification and the owner panel; 6) rollback: restore the two base URLs and the CSP line.
- **Cost:** adds some hundred KB to the repository. No owner setup apart from approving and, if needed, supplying the files.

## E4. Navigation away and the approved calendar iframe addresses cannot be fully blocked by a page rule
- **Today:** a hostile script could still navigate the page (a link or redirect) or put data in an approved calendar iframe address. `frame-src` also allows many calendar providers (Calendly, GoHighLevel hosts, Cal.com, TidyCal, Acuity, SavvyCal, Google Calendar) although the owner uses one.
- **Risk:** low; needs an injected script first, and the earlier layers (CSP, no inline handlers, escaped text) make that hard.
- **Options and plan:** 1) after the owner confirms the one provider in use, trim `frame-src` to that provider (the provider list in the code stays for the owner panel; the CSP is what narrows) with a test that CSP and in-use provider agree; 2) keep the iframe sandbox and `no-referrer` already in place; 3) optionally add a `navigate-to`-style protection is not available in browsers today, so it is documented as a residual risk rather than promised.
- **Needs from owner:** which calendar provider stays (Calendly was used in the live test).

## E5. No independent review
- **Today:** all tests were written by the assistant and run with the owner. The rules checks use a home-made interpreter plus the official emulator in GitHub Actions (passed 206/206).
- **Risk:** blind spots that the author cannot see.
- **Options:** (a) prepare a review pack and ask a person you trust to try to break the live site within agreed limits; (b) a free automated scan of the live site (headers, TLS, mixed content) and a Firebase rules review by someone else; (c) a paid tester later if the site grows.
- **Plan (I can do the preparation only):** a `SECURITY-REVIEW-PACK.md` with scope, the live URL, what is in and out of scope (no attacks on Google, GitHub or Cloudflare themselves), the threat list, the rules text, the test list, the known limits, how to report, and a fix-tracking table; plus a short owner checklist for running an automated scan.
- **Needs from owner:** deciding who reviews and when. I cannot perform or certify an independent review.
