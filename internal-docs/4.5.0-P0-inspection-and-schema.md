## 2. New in P0

### 2.1 Client ID registry
`clientRegistry/{CLIENTID}` - the document ID **is** the Client ID.

```
{ status: "active" | "archived", notes: string(<=500), createdAt: serverTime, updatedAt: serverTime,
  rev: number (1 at creation, +1 on every change), lastAudit: string(16-40 letters/digits) }
```
`clientRegistryAudit/{auditId}` - append-only.
```
{ clientId, action: "create" | "status" | "notes", prev: string(<=500), next: string(<=500),
  reason: string(<=200; at least 3 characters for "status"), rev, actor: ownerUid, createdAt: serverTime }
```
Rules (see `firestore.rules.strict`):
- Client ID: `^[A-Z][A-Z0-9-]{1,22}[A-Z0-9]$`, no `--`. No underscore, so invoice IDs built from it are unambiguous.
- No delete and no rename. A rename in a later phase will be an alias record plus an audit entry.
- Every registry create or update must be in the **same batch** as a brand-new audit record that its `lastAudit` points to (`!exists` before, `existsAfter` after). The audit record in turn must match the registry entry (`getAfter`): same `rev`, same old/new values. So neither can exist without the other.
- `rev` must go up by exactly one, so two tabs cannot overwrite each other (the second write is refused).
- Personal data cannot be written: the field list is fixed.

Numbering format is stored in `ownerPrivate/clientIdFormat` as `{ prefix: 2-6 letters, digits: 3-6, start: >=1, year: "" | "20xx" }`. It only affects the *next* suggested ID.

### 2.2 Shared libraries (browser and Node, unit tested in `scripts/core.test.mjs`)
- `core-ids.js`: Client ID validation, numbering format, invoice ID layout `CLIENTID__YYYYMMDD__YYYYMMDD`, idempotency keys and payload hash (retry with a different payload = conflict).
- `core-money.js`: supported currencies with minor-unit exponents (USD 2, GBP 2, EUR 2, AUD 2, CAD 2, PHP 2, JPY 0, KWD 3), text-to-integer parsing, one half-up rounding at the invoice total.
- `core-time.js`: UTC differences, IANA zone validation, local-day splitting that is correct across midnight and daylight-saving changes, month-end clamping.
Only `core-ids.js` is loaded by the site in P0. `core-money.js` and `core-time.js` are tested but not loaded until the billing and WorkTrack phases need them.

### 2.3 Backup
`clientRegistry` and `clientRegistryAudit` can be included in the normal backup as **export-only**: they are saved for your records but never restored, because a plain restore would break the rule that ties each change to its audit entry.

## 3. Patterns that later phases will reuse
| Pattern | How it works | Used by |
| --- | --- | --- |
| Paired audit write | One batch: the change plus a fresh audit record; rules check both directions. | Registry (now), WorkTrack corrections, payments |
| Counter-keyed IDs | A head document holds the last counter; the next record's ID must be counter + 1, so a second writer using the same counter is refused and a fork cannot be created. | WorkTrack chain, ledgers (W3) |
| Deterministic IDs | The ID is built from the facts (client + period), so a retry cannot create a duplicate. | Invoices (B2) |
| Append-only notifications + read marks | Notifications are create-only; read state is separate create-only marks and a "read up to" marker. | B3 |

Planned collections (not created in P0): `timeSessions`, `timeEvents`, `timeCorrections`, `timeHead`, `billableEntries`, `invoices`, `payments`, `notifications`, `notificationReads`, `leadMeta`. Their shapes are defined in the Rev 2 strategy document and will be written into the rules in the phase that introduces each one.

## 4. Migration specification (for B1 and M3; nothing runs in P0)
1. Back up (normal and library).
2. Count existing `clients` and `meetingRequests` documents and how many contain personal fields.
3. Assign Client IDs to existing clients (the owner confirms each proposed ID).
4. Export the personal fields to the owner's private Sheet, read them back, and compare counts and field hashes.
5. Only when every check passes and the owner approves in writing: remove the personal fields from Firestore.
6. Review other places that may hold personal data (calendar event titles and descriptions, old backup files on the owner's computer) and list them in the migration report.
Pass criteria and the report format are in the Rev 2 strategy (section 4.7).
