# 4.5.0 SV1: employer testimonial survey

Status: AUTOMATED_TESTED, waiting for the owner's live test (`SV1-CHECKLIST.md`). Phase SV2 (custom surveys, 3-month reminder from the Client ID start date, retention, backup export) is designed but NOT built.

## What it does
1. Owner Panel > **Employer surveys** > "Send a survey": employer name, e-mail, optional company, your name, optional Client ID.
2. The panel makes one personal link `survey.html#k=KEY` and opens the owner's own mail program with the message ready (or copies the link / message).
3. The employer opens the link and sees the survey made for them only: 1 to 5 stars, a message (20 to 700 characters), "what did they do best" (optional), would hire again (yes/no), an optional link to a short video (YouTube, Loom or Google Drive; never an uploaded file), the name / role / company to show, and a required consent to publish.
4. The answer reaches the owner as "Answers to review". Nothing is public. **Approve** copies it into Testimonials as a **hidden** item (the section switch and view are left as they were); **Reject** keeps it for the records and never publishes it.

## The key
- 32 random letters and digits (about 190 bits, `crypto.getRandomValues`, rejection sampling so no character is more likely).
- It is the Firestore document ID of the invite and of its one response, so "does the key exist?" is checked by the database rules, not by the page.
- It travels after `#`. Browsers never send the part after `#` to a server, GitHub Pages logs or a Referer header. The page also sends `no-referrer`, and removes the key from the address bar after a successful send.
- One use: the submit is ONE batch (create the response + flip the invite from `sent` to `submitted`). The rules accept it only if the invite is `sent`, not expired (60 days), the site is not paused (`content/guard.pause`), and both writes are present.
- Revoke: the owner can switch a `sent` invite to `revoked`; it then answers like a wrong key.
- Wrong, missing, expired, revoked or used keys all show the same neutral page. The page never says why.

## Data (all in `firestore.rules.strict` and `firestore.rules`, identical text)
| Collection | Who | Holds |
|---|---|---|
| `surveyInvites/{key}` | owner creates / revokes; the key holder can `get` ONE while it is `sent` and unexpired; nobody can list except the owner | `surveyVersion` (`default-1`), `employerName`, `company`, `ownerName`, `status`, `createdAt`, `expiresAt`, `submittedAt` after use. **No e-mail, no Client ID.** |
| `surveyInvitesPrivate/{key}` | owner only | `employerEmail`, `clientId`, `createdAt` |
| `surveyResponses/{key}` | a visitor can only create it (with the invite flip); owner reads, decides once, deletes | `rating`, `comment`, `best`, `recommend`, `videoUrl`, `displayName`, `displayRole`, `displayCompany`, `consentPublish` (must be true), `submittedAt`, `ownerStatus` (starts `pending`), then `decidedAt` and (approved only) `testimonialId` |

Rules limits equal the page limits (checked by `scripts/survey-guard.test.mjs`): key 32 letters/digits; message 700 (the limit of a published testimonial); best 500; name 80; role 80; company 100; video link 300 and YouTube / Loom / `drive.google.com` only; rating a whole number 1 to 5; expiry at most 61 days ahead.

## Security notes
- **No Worker guard on this page (deliberate, differs from the layout I first described).** The meeting form needs the Worker because anyone can open it. Here the only way to write is a valid, unused, unexpired 190-bit key that only the owner can create, so a bot cannot spam it. Adding the Worker would add a dependency and a new failure point without removing a risk. If you ever make survey links public (not recommended), add the Worker then.
- `survey.html` has its own CSP: `default-src 'none'`; scripts `'self'` + the Firebase SDK host; connections only `firestore.googleapis.com`; no inline script or style, no frames, no forms, `base-uri 'none'`. It is `noindex, nofollow`, not in the sitemap, and keeps the frame-guard.
- Everything the employer types is untrusted. The page and the owner panel build it with `textContent` / DOM nodes only. The video link is shown only after the same parser accepts it, opens in a new tab with `noopener noreferrer`, and is never embedded.
- **Honest limit:** the key proves "a link the owner created was opened and answered once". It cannot prove the person is a genuine employer; anyone who receives the link could answer. Mitigations: send it only to the employer's e-mail, check the name / company / video yourself before approving, approval is manual, and an approved item arrives hidden.
- Google Drive links can be changed or removed by their owner later, and the page cannot check the sharing setting. The employer is asked to set "Anyone with the link"; the owner opens the link before approving.
- The emergency pause (Security > Abuse protection) also stops survey answers.
- App Check: not enforced today. If E1 (App Check enforcement) is ever switched on, `survey.html` needs the reCAPTCHA hosts in its CSP and App Check started in `survey-page.js`; `survey-guard.test.mjs` fails if a site key is set and this was not done.

## Tests
- `scripts/core-survey.test.mjs` (23): key generation, bias, `#k=` parsing, link, video links (accept / look-alike hosts / credentials / ports), text cleaning, validation edges, invite usability, labels, testimonial mapping, e-mail text.
- `scripts/survey-guard.test.mjs` (13): page CSP exact, noindex / referrer, no inline code, ids exist, no `innerHTML`, no network except the SDK, the batch shape, owner page safety, limits equal the rules, both rules files identical, App Check rule.
- `rules-tests/attack/attack_cases.py` section 8m (both rules files x 34 checks) -> 2527 checks in total. Two mutation sets weaken the survey rules one clause at a time: `mutations_sv1.py` (65 hand-written, all caught) and `mutations_sv1_gen.py` (150 generated the same way as the B2 set: every clause replaced by `true`, every comparison flipped; 134 caught, 16 listed in `sv1_equiv.py` with the reason each is a guard that another clause repeats, for example the pause is checked in both writes of the batch). The generated run found four real gaps in my first tests (revoke and owner decision freezing every other field, a link of exactly 300 characters, lists passed as text); they are now covered. The survey block sits after `match /clients/{id}` and ends with `// end SV1`, so the older B2 generator does not mix with it.
- `rules-tests/attack/sv1_replay.py` replays the exact writes the real page made (`sv1_captured.json`, recorded by the browser test) against the real rules text: accepted, and 9 kinds of tampering refused, plus expired / revoked / used / paused.
- `rules-tests/browser/sv1-1-survey.mjs` (94): the real page with its real CSP (fake SDK), every failure path, hostile text, CSP blocks outside fetch / script / image / frame / style, 360 px layout and targets, themes, and the whole Owner Panel page (create, e-mail, copy, revoke, delete, approve, reject, retry, badge, sign-out).
- `rules-tests/emulator/survey-sv1.test.mjs`: the same rule cases for the official emulator (GitHub Actions). **Written, not executed** in the build environment.
- All earlier suites re-run green (418 unit, the 13 older browser suites).

## Not in SV1 (SV2 or later, none approved to build)
- Custom surveys (own questions), the 3-month reminder from a Client ID start date (needs a `startDate` field and rules change in the Client ID registry), automatic deletion of old invites, adding the survey collections to the backup export and the restore list, a line in the public privacy notice. Until then: delete finished invites by hand; the export does not include survey data.
- Sending e-mail by itself (needs a mail provider and a secret in a Worker).
- Uploading a video file (Firebase Storage needs a paid plan; links are used instead).
