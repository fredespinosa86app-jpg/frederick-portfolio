# 4.5.0 W2 - Client assignment schema and rules (internal)

This repository is public. Nothing secret belongs in this file.

## Collections (owner only, no delete)
| Path | Fields | Notes |
|---|---|---|
| `workAssign/{sid}__{CLIENTID}` | sid, clientId, status (active/removed), rev, addedAt, updatedAt, lastAudit | One record per client per session. Created `active`, rev 1. Update flips status, rev +1. |
| `workAssignAudit/{aid}` | sid, clientId, action (add/remove/readd), reason (<=200), rev, actor, createdAt | Create-only. Brand-new id in the same batch as the assignment change. |

## Rules in plain words
- Session must be open after the batch (`wkOpen`): the state record names this session and is not NOT_STARTED. At clock in, the new state counts, so clients can be saved in the same transaction.
- New assignment: the registry entry must exist and be active (`regActive`). Re-adding a removed client is an update and also needs an active client. Removing needs no active check.
- Audit entry links to the assignment (lastAudit, rev), add iff rev 1.
- Not enforceable in rules: the 10-client limit (page only).
