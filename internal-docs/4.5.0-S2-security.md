## S2-D
- `core-authcleanup.js`: due when never done, 30+ days ago, or the stored date is in the future; snooze hides it up to 7 days (snoozes beyond 7 days are ignored).
- Stored in `ownerPrivate/config` as `authCleanupAt`, `authSnoozeAt` (owner-only, existing rule, merge writes). The panel only reminds; nothing is deleted by code.
- Why no automation: a user-deleting service account is a lock-out risk for the owner (rules are tied to the owner's uid; deleting the owner's Auth user and signing in again creates a new uid).
- `m_` users are created only when the page signs in with a Worker token; they hold no name, email or phone.

## S2-C1
- `core-connlog.js` + `owner-s2.js`: a PerformanceObserver (type resource, buffered) while the owner is signed in; only fetch/xmlhttprequest/beacon/other entries; stores `{origin: {n, first, last}}` in localStorage (`connLog:v1`), max 60 hosts, host only (no path or query). Entries made while signed out are skipped when logging resumes. Visitors record nothing.
- `EXPECTED` hosts come from the code scan: firestore, identitytoolkit, securetoken, forms Worker, www.googleapis.com, script.google.com + script.googleusercontent.com, www.youtube.com, dns.google, App Check hosts. Unknown hosts are marked, never blocked.
- Limits: requests inside workers or iframes are not seen.
- Why a log first: the CSP is a `<meta>` tag and cannot run in report-only mode, so a wrong list would break features with no warning.

## S2-B (delivered)
Facts (Cloudflare docs): the Workers Rate Limiting binding needs a `ratelimits` entry in the Worker config (Wrangler 4.36+), window of 10 or 60 seconds, counts per Cloudflare location and approximate, free-plan availability not stated. WAF rate-limit rules on the Free plan: 1 rule, 10 s window, IP only, path field; they attach to a domain (zone), so a custom domain is needed. Proposed limits per IP+route per 60 s: challenge 5, verify 10, status 30; existing in-Worker limits stay as the second layer.

### S2-B as built
- Three Rate limiter bindings (dashboard): `RL_STATUS` 30, `RL_CHALLENGE` 5, `RL_VERIFY` 10, each per 60 seconds, keyed by the visitor address (`CF-Connecting-IP`). Different limits per route need separate bindings.
- Worker (`server/portfolio-forms-worker.js`): after the origin check, before any work; 429 `{error:'slow'}` with `Retry-After: 60` and the CORS header, which the page already shows as "Too many attempts". Refused origins, preflight and unknown paths never touch a binding.
- Fails OPEN: missing binding, binding error or an unknown address skips the binding; the in-Worker limits (8 challenges, 3 tokens, 12 wrong codes per address per 10 minutes) and the daily cap in the rules remain the backstop.
- A limited verify does not use up a challenge (the check happens before the challenge is read).
- `GET /v1/status` now includes `rl: true` only when all three bindings are present, for the owner's check.
- Known behavior: a rate-limited status check makes the page report "unreachable" when verification is ON; at 30 a minute this does not happen to real visitors.
- Cloudflare documents that counts are per location and approximate.
- The WAF rate-limiting rule and the custom-domain move are not needed (the owner's domain `frederickespinosa.com` is at Hostinger and not in use).
